# Internationalization and localization

> Helps a developer or reviewer build software that adapts to any language, script and region, and
> keep its translations valid, complete and testable.

## When it applies
- Adding or changing user-visible text: labels, messages, notifications, errors.
- Displaying dates, times, numbers, currencies, lists or counted quantities.
- Storing, scheduling or exchanging dates, times, numbers or money, or case-mapping identifiers.
- Supporting a new language, region or script, right-to-left scripts included.
- Designing an API, file or storage format that carries natural-language strings.
- Upgrading locale data or the library that ships it.
- Sending strings to translators or importing translations.

## Method
1. Externalize every user-visible string into message catalogs under stable keys; build no sentence
   in code.
2. Write each message as one complete sentence; put plural, gender or other selection at the
   outermost level, with a full sentence in each variant, at most one level of nesting and always a
   catch-all variant.
3. Take plural categories from CLDR for each target language; never read "one" as exactly 1; add an
   explicit zero variant where the wording is more natural.
4. Format dates, numbers, currencies and lists with locale-aware formatters backed by CLDR data,
   never by concatenation or fixed patterns.
5. Identify locales with BCP 47 tags kept as short as possible: add a script or region subtag only
   when it distinguishes; check subtags against the IANA registry.
6. Attach language and direction to every natural-language string that crosses a boundary: defaults
   per resource, overrides per string, "und" for an unknown language, never a default to
   left-to-right, nothing on identifiers.
7. At display time, isolate every inserted value from the surrounding text, and lay out with logical
   start and end positions so the interface mirrors for right-to-left locales.
8. Give translators context with each message (meaning, placeholders, length limit) and protect
   non-translatable content with the interchange format's translate annotation rather than masking
   it.
9. From the first builds, run an accented, expanded (about 40% for an English source), delimited
   pseudo-locale and a mirrored one, under well-formed codes that can never name a real locale.
10. Pin the locale data version; on each upgrade, read the release notes and review changes to
    plural rules and regional preferences before shipping.
11. Decide which kind of time each value is before formatting it: store and exchange instants in
    UTC; keep future and recurring events as local time plus an IANA time zone ID, never an offset
    alone; leave floating values such as birthdays and opening hours without a zone; let each user
    choose a time zone, kept with the profile; update the time zone data on its own schedule, even
    when it ships inside the library whose locale data is pinned, and recompute stored future
    instants when its rules change.
12. Keep values that software reads locale-neutral: serialize numbers, dates and money, as an amount
    plus its currency code, in locale-independent forms; case-map identifiers, keys and protocol
    tokens with root-locale or ASCII-only rules; pass an explicit locale to every case mapping,
    parsing and formatting call rather than relying on the process default; use the user's locale
    only for what a person reads.
13. Store, exchange and serialize text as UTF-8, the only encoding a new format accepts; set a
    length limit only where a real constraint needs one, state its unit (code points by preference,
    bytes only as a last resort and never splitting a code point), and truncate on grapheme cluster
    boundaries with a visible mark of the cut.

## Reflexes
- Can a translator reorder every part of this sentence without touching code?
- Does this test pin an output that the next locale data release may change?

## What is measured
- Message validity: messages with a syntax or data-model error, target zero; a verify step runs the
  message parser over every catalog and fails on any error.
- Placeholder parity: translations using a variable the source message does not define, target zero;
  a verify step compares variable sets per key and locale.
- Plural coverage: plural messages missing a category that CLDR defines for their locale, target
  zero; a verify step checks them against a category list generated from the pinned CLDR version.
- Catalog completeness: missing and orphan keys per locale; the verify step fails on orphans, and on
  missing keys only for locales declared complete; that threshold is judgment.
- Pseudo-locale defects: visible strings with no delimiter, several delimiter pairs or a lost end
  delimiter, in interface tests run in the pseudo-locale, user data excluded; a verify step fails on
  any.
- Identifier and metadata validity: locale tags are well-formed and registered; localizable fields
  carry or inherit a valid language and a direction of ltr, rtl or auto; a verify step validates
  fixtures.
- Locale data drift: a regenerated snapshot of locale metadata differs from the committed one; the
  verify step fails until the change is reviewed and committed.
- Zoned times: future or recurring event times stored with an offset but no IANA time zone ID,
  target zero; a verify step checks schemas and fixtures, date arithmetic tests cross a daylight
  saving transition, and a scheduled check flags time zone data older than the latest IANA release.
- Default-locale calls: case mapping, parsing and formatting calls that omit an explicit locale,
  target zero; a verify step runs a static check that flags them, switched on explicitly where the
  analyzer ships it off.
- Text round-trip: fixture strings with supplementary characters, combining sequences and emoji
  sequences that come back changed or invalid from a storage or interchange path, or cut inside a
  grapheme cluster by truncation, target zero; a verify step sends them through every such path.
- Judgment, not measured: translation quality, cultural fit, and review of right-to-left screens by
  a reader of the script; pseudotranslation is not a complete replacement for validating the
  translated application.

  rule changes, 24-hour preferences, ISO weeks planned for CLDR 50.

  2026-11-01: error categories, mandatory catch-all variant, stability policy.

  categories, "other" required, "one" wider than 1, zero messages.

  Pseudolocalization](https://learn.microsoft.com/en-us/globalization/methodology/pseudolocalization),

  IANA zone IDs rather than offsets for future and recurring events, floating values, a user-chosen

  Classes](https://unicode-org.github.io/icu/userguide/datetime/timezone/), 2026-11-01: bundled time

  Developers](https://www.w3.org/TR/international-specs/), 2026-11-01: UTF-8 as the only encoding

- [Error Prone: StringCaseLocaleUsage](https://errorprone.info/bugpattern/StringCaseLocaleUsage),

- [Microsoft Learn: CA1305 Specify
  IFormatProvider](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1305),

  by default.
